# ASE ODBC browsing and fixed profile key

The user superseded the isql catalog design: connect and browse ASE through
pyodbc, while character-mode file IN/OUT continues using the installed SAP
bcp.exe. Ship the application and pyodbc as one Windows x64 EXE. The user's PC
supplies a registered 64-bit SAP ASE ODBC driver and SAP BCP for transfers.

Keep one ODBC connection per application session and serialize cursor use.
Autocommit catalog reads avoid persistent transactions; login and query timeouts
remain bounded. Disconnect, expired sessions, shutdown and late/canceled login
must release connections. Active queries support cursor cancellation. Verify ASE
identity and retain explicit Search/Enter, optional owner, escaped identifiers,
parameterized literal search, exact object and complete schema checks.

Optional [odbc] driver in ase-connections.txt selects the registered driver.
Otherwise find a SAP/Sybase ASE driver; never choose SQL Anywhere, Microsoft SQL
Server or FreeTDS silently. ODBC browsing works independently of BCP availability.
Legacy isql_path is ignored. BCP workers use fresh ODBC metadata validation and
preserve the existing file guard, single-use review, process ownership, numeric
progress, credential redaction and atomic export publication.

For ASE connection profiles only, the user explicitly requires the fixed Jasypt
key nice1234!!. Encrypt/decrypt with that constant and the file's existing Jasypt
algorithm settings. Remove the UI/API master-key input. Keep ENC(...) passwords,
successful-login-only atomic saves, last-server selection and other profiles.
Manual successful saves use host-account as the connection name, including
renaming a matching old profile while preserving its comments and default DB.
Name collisions receive a port/unique suffix and INI delimiters are escaped.
Ciphertext made with another key must fail with a re-enter-and-save instruction;
never guess an old key or rewrite failed profiles. An embedded shared key hides
plaintext in the configuration but does not provide a secret only the user knows.

Verification includes fake ODBC unit boundaries for connection reuse, SQL,
errors, cancellation, schemas and persistence; browser tests for the changed
flow; native Windows ConPTY/BCP tests; and the actual sole EXE's pyodbc extension
import, driver discovery, sanitized missing-driver failure and file preservation.
No actual ASE server or SAP ODBC driver exists in the cloud. Do not describe
fixtures as successful real database connections or measured user-PC performance.
