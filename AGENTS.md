# Project rules

## Distribution

- The user requires every end-user release to be **one Windows 10/11 x64 executable: `nice-tools.exe`**.
- Bundle Python, runtime dependencies and all HTML/CSS/JavaScript assets into that executable. End users need their existing browser; ASE tools additionally use the PC's installed 64-bit SAP ASE ODBC driver and SAP bcp.exe (Windows 10 1809+).
- Start on `127.0.0.1` with an available port and open the local UI automatically. User files stay on the user's PC.
- Keep source-based commands for development. Do not present Python installation, virtualenvs or wheelhouse folders as the normal end-user deployment.
- Build Windows executables on Windows. Before distributing, exercise the actual EXE from a directory containing only that file, including page/assets and a real comparison request.
- A passing source test suite or Linux packaging check does not prove the Windows EXE works. Report any unrun native checks explicitly.
- Do not introduce runtime CDN or Internet dependencies.
- The user-authorized `ase-connections.txt` and `iq-connections.txt` are optional, app-created or user-maintained data beside the EXE, not an additional runtime dependency or required distribution artifact. Keep the release ZIP to the single EXE.

## Workspace

Use the existing isolated cloud checkout. Do not create a Git worktree unless the user explicitly asks.

## File comparison

The user requires no fixed byte-size cap for individual files or complete upload requests. Compare complete contents, including differences beyond the former 10 MiB limit. Keep large-file and large-request regression checks in source tests and executable verification. Actual capacity depends on the PC's memory and temporary storage.

Automatically detect each file's text encoding before normalization and diff. Decode and validate the complete file strictly; detection samples must never truncate comparison, and replacement/ignore decoding must not hide differences. Keep Korean legacy and mixed-encoding regression checks. Do not promise perfect detection of ambiguous short text or BOM-less Unicode.

Windows comparison uses native folder dialogs and direct Python reads, with no multipart upload/reupload in the normal EXE UI. Only opaque session-owned folder tokens, job handles, options and validated relative result paths cross the JSON boundary. Preserve loopback/origin/custom-header/no-store protections. Keep non-Windows development upload fallback only when the status explicitly says native selection unavailable; do not silently fallback on status errors.

Use the owned --comparison-worker process tree for scanning/comparison/initial diff generation; cancellation must be checked atomically with process registration and kill only the target job. Close/eviction must terminate owned work before cleaning caches. Reject/fail safely on moved/replaced sources; revalidate missing counterpart paths before one-sided cached diffs. Never follow descendant symlinks/junctions, including queued-directory replacement races: keep Windows non-delete-sharing no-reparse directory handles and POSIX no-follow scandir descriptors. Source files remain unchanged.

Byte-identical pairs still require full strict text validation once (invalid binary cannot become same); skip normalization/sorting only after that validation. Normalize streams with the same Unicode/line/trim/whitespace rules as comparison.py. Sort with bounded external runs/merge and preserve duplicates. Reuse owned normalized caches and metadata-last 200-row diff pages; completed pages must not spawn a new frozen EXE or re-decode sources. Matching may still hold one selected pair's line lists; memory also scales with the largest line. Do not promise constant memory or universal speedups. Keep browser cancellation/stale-request/cleanup regressions, actual HTTP-token-to-worker integration, and real frozen worker full-file/mixed-encoding/late-difference/page/change-detection checks.

## Validation

Jasypt changes must pass the real Java Jasypt 1.9.3 bidirectional check (`scripts/check_jasypt_java.py`), not just Python round trips. Keep the pinned Java reference fixtures and executable checks for both AES and MD5/DES settings. The default is `PBEWithMD5AndDES` with NoIvGenerator; retain AES support with RandomIvGenerator. Java is for developer validation only; ASE uses the PC's SAP ODBC driver and BCP and otherwise user PCs need the single EXE and a browser. Never persist passwords/plaintext in logs or browser storage, and keep Jasypt API responses `Cache-Control: no-store` with sanitized validation errors.

Run the source suite with the project's virtualenv: `.venv/bin/python -m pytest -q` on Linux or `.venv\Scripts\python -m pytest -q` on Windows. Windows CI must run source tests, build the single EXE and verify the executable before uploading it as the distribution artifact.

## ASE / BCP

- OUT supports selecting multiple tables/views and choosing 1–5 concurrent transfers (default 3), with a maximum of five across the app. Queue only the selected number initially and replenish on completion; queued work must not block pool threads waiting for a per-batch slot. Default the output folder to the actual EXE directory (repository root in source mode); a native folder picker selects another location. Automatically create `database.owner.table.txt` directly inside that folder (no owner subdirectory), then `database.owner.table_1.txt`, `database.owner.table_2.txt` on collisions, using atomic no-replace publication so external files are never overwritten. Keep safe Windows names and reject output-folder escapes. IN remains one table and one selected local file. Start both modes directly without a user preview/review confirmation; retain automatic schema/full-file checks, read-sharing guards, cancellation ownership and single-session transfer locks. Show per-object queued/running/success/failure, paths and OUT metrics; a failed export must not prevent other queued exports.
- DB/filter changes must not fetch objects automatically. Search/Enter explicitly queries the server, with an optional owner (all owners by default) and literal, case-insensitive name/kind filters. Owner choices may load on demand. Preserve exact owner/object/schema checks for BCP even when browsing all owners.
- Allow IN mode selection after connecting when BCP is available, before choosing a table or loading columns. Keep mode changes locked during requests, native dialogs and active transfers. IN execution still requires one table with loaded schema and one native-file token; OUT checkboxes do not select an IN table. Show the next required step and retry guidance on column-query failure. Default BCP encoding to EUC-KR and field terminator to | in both UI and canonical options; keep LF row terminator and explicit format overrides.
- Catalogs use bundled pyodbc with the PC's registered 64-bit SAP ASE ODBC driver. Maintain and reuse the connected session for browsing; close/cancel it on disconnect/shutdown/error. Timing diagnostics must remain secret-free and distinguish total, login, query and app preparation. Worker pretransfer schema checks use a separate ODBC connection. Do not claim measured user-PC speed improvements from mocks.
- Connect directly with host, port, user and password. Do not select ODBC DSNs or read the user's SQL.INI for catalogs. Ignore legacy profile `dsn` and `[sap_client] sql_ini_path` while preserving existing encrypted configuration data and comments; never require deleting the user's file. BCP still creates its own temporary endpoint-only SQL.INI. Keep driver names braced and escape other ODBC values only when required by connection-string syntax.
- Read UTF-8 INI profiles from `ase-connections.txt` beside the actual EXE, or repository root for source execution, independently of CWD and bundle extraction path. On successful new connection, atomically save metadata and Jasypt-encrypted DB password (`ENC(...)`), preserving existing sections. Name saved connections with the entered server address and account (`server-account`), adding a safe suffix for collisions. Failed login must not save; failed persistence must retain the successful session and show a sanitized warning. Remember the last successful profile for the next launch; use the user-required fixed profile key `nice1234!!` without a key input UI. Reject caller master_password fields. Standalone Jasypt still accepts its own key.
- Resolve the PC's installed `bcp.exe` through `[sap_client] bcp_path`, then PATH/SYBASE/SYBASE_OCS when unspecified. Legacy isql_path is ignored; do not require/invoke isql. Pick a registered SAP ASE ODBC driver or the exact `[odbc] driver` name. Missing BCP must not block ODBC browsing. Explicit invalid paths/driver names must fail. Never bundle/download SAP clients, FreeTDS or ODBC drivers, or substitute INSERTs for BCP.
- Never persist plaintext DB passwords in files, arguments, environment variables, logs or browser storage. ODBC receives credentials only in memory. SAP BCP uses the owned Windows ConPTY Password: prompt, not `-P`; isolated workers receive credentials through stdin. Keep responses no-store and retain the loopback/custom-header boundary.
- Print the complete BCP command and endpoint to the launcher console before execution, redacting before quoting and displaying control terminators as escaped text. Route command records only to the console. Failed jobs must show sanitized SAP console diagnostics in their web error and console failure block, with object/direction/exit context; retain at most the first/last 8,192 log characters in errors, marking truncation. Continue streaming the full sanitized output to the console. Warn about remaining committed batches only for IN failures.
- Use the same console path for direct IN and batch OUT: log target/direction start, worker status (including IN prevalidation rows/bytes), actual command, full sanitized SAP stream, and outcome. Defer app status while the streamed redactor has a pending suffix, flush it after the SAP stream, and redact each complete status independently; inserting status must never interrupt SAP text or change secret matching across chunks. Keep console-only command/output records out of web progress events and tolerate unavailable stdout.
- IN appends. Completed batches may survive failure/cancel; show this before execution. Revalidate reviewed schema and complete input file, and hold Windows read-sharing guard through SAP transfer.
- Publish OUT only after success under the parent's cancellation lock; preserve an existing destination on failure/cancel and kill the owned worker/SAP process tree.
- Parse the final BCP count both as a standalone `N rows copied.` line and immediately after the known no-newline `Starting copy..` / `Starting copy...` banner. Preserve whole-line matching, chunk/EOF buffering, pre-redaction semantic parsing, exit-code and full-stream error checks; do not accept arbitrary text containing a count or progress-only totals as success. Keep native Windows console fixture coverage of the joined summary.
- Windows CI must compile a developer-only BCP console fixture before source tests and exercise native console password input. Verify actual EXE native pyodbc 5.3.0 import/discovery, graceful missing/invalid-driver failure, fixed-key profile decoding, ignored legacy DSN/SQL.INI fields and failed-login nonpersistence. Keep source mock tests for ODBC reuse/catalogs/autosave/schema/transfer control; do not create a fake runtime ODBC backdoor or claim frozen successful ASE transfers without a real server. Fixtures are not distribution artifacts; report real-server charset, identity, LOB and date checks separately.

- Render IN execution in the same result table and status counts as OUT, using one row for its selected table/input path, running/completed/failed/cancelled state, rows and detailed messages. Preserve the IN partial-batch warning and single-file/single-table payload; never turn IN into a batch transfer.

## SAP IQ

- Use bundled pyodbc with the PC's registered 64-bit SAP IQ/SQL Anywhere ODBC driver. Never bundle/download proprietary drivers or select an ASE driver as an IQ fallback. Show missing-driver guidance without disabling the other tools.
- Accept one SELECT / WITH SELECT; preserve quoted SQL/comments, reject scripts and SELECT INTO. Use read-only connection attributes, autocommit false and rollback/close; do not promise protection from function side effects beyond DB privileges.
- Connection verification and each export have separate owned native worker connections; credentials stay only in memory/stdin. Reuse owned Windows Job/process-tree cancellation and the app's shared maximum-five dispatcher. Never persist plaintext IQ passwords, SQL or row values in logs/browser storage.
- Export all results with fetchmany, default EUC-KR/pipe/LF/no header, strict values without silent replacement or truncation. Parent reserves the stage and publishes atomically without overwriting only on success under its cancellation lock. Output defaults to actual EXE directory, flat editable basename with collision suffixes. No final output on failure/cancel; native folder picker alone changes the output directory.
- Keep IQ API loopback/origin/custom-header boundaries and no-store responses. Test disconnected HTTP connection cleanup, progress/cancel, frozen --iq-worker imports and graceful missing-driver errors. Report actual IQ driver/server integration as untested when unavailable.
- Preserve pyodbc's initial zero/unlimited IQ query timeout without assigning connection.timeout. Even assigning zero invokes SQLSetConnectAttr(SQL_ATTR_CONNECTION_TIMEOUT), which some SAP IQ drivers reject after successful login. Login timeout remains 15 seconds; cancellation owns/kills the worker. Report cursor allocation as cursor-open separately from connect and IQ-identity; never hide a cursor error or expose native diagnostics.
- IQ saved connections use separate UTF-8/BOM iq-connections.txt beside the actual EXE (repo root in source), independently of CWD/MEIPASS and ASE data. On successful verification, atomically save direct host/port/user/database/server_name/driver metadata and Jasypt ENC(...) password with the same user-required fixed key nice1234!! as ASE. Name profiles host-account with safe collision suffixes, distinguish databases/engines on the same endpoint, remember/preselect last success, and reconnect through an opaque current profile ID without returning ciphertext/password to the browser. Failed login must not save; failed persistence retains the verified session with a sanitized warning. Preserve comments, other profiles and Jasypt settings; reject corrupt/stale/plaintext files without overwriting them. Bundle iq_profiles and verify encrypted profile reading plus failed-login nonpersistence in the actual EXE.
- Preserve typed, value-free IQ export diagnostics across worker JSON: strict format failures include a fixed reason code, one-based row/column (header row 0) and canonical encoding. Distinguish fetch failures and trusted ODBC SQLSTATEs from writing failures; recognize unsupported SQL type/zero-based column only from the exact pinned pyodbc template and convert the column to one-based. File write/flush/close errors expose only numeric errno/winerror plus fixed guidance. Never format raw native exception strings, SQL, column names or cell values into errors. Flush before reporting writer success; failed stages remain unpublished and owned cleanup precedes terminal failure.
- Print sanitized IQ connection/export failures to the existing launcher console using the shared tolerant console writer. Redact each complete record before escaping controls; unavailable stdout must not affect the operation. Keep worker stdout JSON-only and do not create a second console or a persistent log. Verify the real frozen launcher emits an IQ connection failure/phase without credentials. A generic writing screenshot after successful verification does not establish an encoding, type or disk root cause; report this as improved diagnostics until the user's real driver/data supplies a concrete reason.
